# Server and API capabilities for classification strategy

Status: source-code inventory for strategy decisions, 2026-10-11. This describes capabilities present in this repository, not an approved classification architecture or a deployed classification API. It is based on local source and documentation inspection; no server, Firebase database, Google Sheet, or live-data job was contacted. The classification requirements and product decisions live in the sibling `lpu-belt-explorer/internal-docs/classification-functionality-overview.md`.

## Decision-relevant picture

The Node service is a viable place to build a trusted classification API: it already hosts Express routes, verifies Firebase ID tokens, selects a configured Firestore database through Firebase Admin, and separates route validation from service data access. It also has generated-summary readers and export jobs. **It has no classification vote, admin-action, changelog, round, or publication endpoint today.** Its versioned API is request/response HTTP; it has no existing classification subscription or push channel. Choosing it as the data owner would therefore require new routes, data contracts, authorization, freshness behavior, tests, and deployment coordination with the React app. [Server entry](../src/lpubeltsApiServer.js), [route registration](../src/routes.js), [versioned router](../src/api/index.js).

| Classification need | Existing surface that may help | Gap or design consequence |
| --- | --- | --- |
| Per-user lock/scorecard vote indicator, updated in real time | Verified Firebase identity and direct Firestore reads are available; the frontend already calls this API for profiles and lock videos. | No vote endpoint or server push exists. Ordinary HTTP fetches/polling would not meet the stated real-time own-vote requirement by themselves; compare a Firestore client listener or a new push mechanism with an API read. Avoid one request/subscription per lock row. |
| On-demand modern vote detail | Versioned resource routers and service modules provide a pattern for bounded per-lock reads. | Add an explicit eligible-reader policy for comments/media URLs and a bounded query/response; current public profile and video endpoints are not an authorization model for modern votes. |
| Live admin worklist and near-real-time other readers | Firestore Admin can query a named database; service code can aggregate or project rows. Generated JSON services show another read model. | No classification query, projection, or invalidation exists. A public/generated static file cannot hold access-controlled vote detail. Decide whether live updates come from client Firestore listeners, polling, or a new server channel. |
| Vote create/edit/delete and admin-action transitions | `requireAuth` supplies verified UID/claims; existing administrative legacy routes show role middleware and rate limiting. | New classification writes must enforce ownership/admin claims, field validation, timestamps, concurrency and idempotency on the trusted side. Existing admin middleware checks unrelated `raflAdmin`/`lpuAdmin` claims. |
| Published changelogs, round history, and manual reconciliation | API can serve Firestore records, and catalog helpers can load `data.json` from a reviewed local snapshot or bounded HTTPS source. | No publication event store, comparison endpoint, or classification-aware catalog join exists. The current site catalog is produced by the frontend repository's manual Sheet import; this server does not publish that catalog. |
| Later direct Sheet update | The repository includes `googleapis` and a separate RAFL Forms/Sheets utility. | Current Google Sheets authorization requests `spreadsheets.readonly`; it is not a write-ready classification integration. New credentials/scopes, permissions, failure handling, and reconciliation would be required. This is a later phase, not a current requirement. |

## Current HTTP surfaces and data boundaries

`src/lpubeltsApiServer.js` configures URL normalization, Helmet, JSON body limit, request IDs, structured logging, CORS, static files, an IP baseline rate limit, and centralized errors before/after route registration. `src/routes.js` mounts health/readiness, lazy legacy service bundles, and `/api/v1`; legacy routes may also be mounted under a configurable `/services` prefix. The server normalizes duplicate leading slashes that can arrive through its proxy. The versioned API follows a `{metadata, data}` success envelope and a structured error with `requestId`; the [OpenAPI spec](../src/api/documentation/openapi.yaml) and [API guide](../src/api/documentation/README.md) are the contract artifacts for new endpoints. Code is the source of truth where docs lag: for example, `GET /api/v1/stats/collections/locks/wishlist` exists in the router but is not listed in the current OpenAPI paths. [Server](../src/lpubeltsApiServer.js), [routes](../src/routes.js), [API router](../src/api/index.js), [collection routes](../src/api/routes/collections.js).

The lazy legacy services include request-lock, update-request, and request-vote POST routes; media upload and Flickr information; email form delivery; Firebase activity logging; and admin-gated RAFL preview and Reddit-belt refresh operations. They demonstrate route bundles, injected runtime handlers, external-service integrations, and per-route rate limits. Their request votes are for ranking requests, **not classification modern votes**. Health and readiness endpoints are operational probes. New externally consumed classification contracts fit the versioned `/api/v1` route/service pattern rather than adopting an unrelated legacy bundle. [Legacy registration](../src/routes.js), [request-vote router](../src/projects/requestLock/requestVote.bundle.js), [RAFL preview router](../src/projects/importRaflData/importRaflData.bundle.js).

| Current `/api/v1` route family | Backing data | Access and cache | Classification relevance |
| --- | --- | --- | --- |
| `GET /users/:id`, `/summary`, `/wishlist` | Live `lockcollections` Firestore document, reduced public response | Public; `public, max-age=60` | Demonstrates live Firestore reads and allowlisted public shapes, but public data is unsuitable for private modern votes. |
| `GET /users/:id/profile` | Full `lockcollections` document | Firebase bearer token; caller UID or `admin` claim; `private, no-store` | Shows owner/admin enforcement and token forwarding from the frontend. A classification reader rule needs its own claims/profile checks. |
| `GET /locks/:lockId/videos` | Generated `lockVideos.json`, derived from evidence | Public; `public, max-age=300` | Already supplies a scorecard video URL used by the classification vote form; it does not store or authorize votes. |
| `GET /stats/collections/locks` and `/own`, `/scorecard`, `/wishlist` | Generated `collectionStatsByIdFull.json` | Public; `public, max-age=300` | Shows file-backed summary projections and aggregate reads, with export cadence rather than immediate write visibility. |

The profile service caches raw Firestore documents in process memory for 60 seconds (missing documents for 10 seconds, maximum 1,000 entries), then shapes public or private responses. This improves repeated profile reads but can delay recognition of a changed profile-based `blackBelt` role if reused without a separate freshness policy. The generated JSON reader reloads a file when its modification time or size changes, so new files can be served without a server restart; HTTP cache headers and the job schedule still affect client freshness. Rate limits are also process-local: 300 requests/minute baseline per IP, 60/minute for users, and 120/minute for collection stats/lock videos, with backoff after rejection. Classification polling or writes need their own capacity/rate policy, especially if many visible locks are fetched separately. [Profile service](../src/api/services/userProfileService.js), [JSON cache](../src/api/util/readJsonCache.js), [rate-limit policy](../src/api/middleware/rateLimitConfig.js), [rate-limit guide](../src/api/documentation/rate-limiting.md).

The sibling frontend already uses `VITE_API_SERVER_URL` for the profile API and lock-video requests, including the classification vote form's scorecard-video suggestion. Its current default is the older `https://explore.lpubelts.com/services` base, while this repository documents `https://api.lpubelts.com/api/v1` as the production versioned API. Any classification API plan should verify which base URL and deployment the frontend actually targets before relying on new routes. [Frontend API context](../../lpu-belt-explorer/src/app/APIContext.jsx), [frontend URL configuration](../../lpu-belt-explorer/src/data/dataUrls.js), [vote form](../../lpu-belt-explorer/src/classification/VoteForm.jsx), [API guide](../src/api/documentation/README.md).

## Authentication, data access, and deployment

`requireAuth` verifies a Firebase bearer ID token and attaches the decoded token to `req.user`. The full-profile route permits only the same UID or an `admin: true` claim. Other legacy admin routes check `raflAdmin` or `lpuAdmin`; neither grants classification authority. For classification, the server would need an explicit reader check for `admin`, `classificationAdmin`, `lpuMod`, `classificationTeam`, or a trusted `blackBelt` profile role; an admin-action write check for `admin`/`classificationAdmin`; and a vote-write check tied to the verified UID or authorized admin. The backend must not trust UI role switches or client-provided `userId`, `displayName`, status, or timestamps as authorization. Profile role freshness and how synthetic modern IDs are handled during migration remain design choices. [Auth middleware](../src/api/middleware/requireAuth.js), [profile route](../src/api/routes/users.js), [RAFL admin check](../src/projects/importRaflData/requireRaflAdmin.js), [Firebase Admin service](../src/api/services/firebaseAdmin.js).

The Firebase Admin service is centralized and import-safe until used. It validates the configured project/service account and selects `FIRESTORE_DATABASE_ID`; development uses the named `lpubelts-dev` database, while production access is separately guarded by `ALLOW_PRODUCTION_JOB=true`. These guards select the data target; they do not themselves implement classification permissions. A new API service can use `getFirestoreDb()` for trusted reads/writes, while a client-Firestore design would instead need independently reviewed Firestore rules. The server has no classification schema, indexes, transaction, or migration code today. [Firebase runtime targets](../.agents/references/firebase-runtime-targets.md), [Firebase Admin service](../src/api/services/firebaseAdmin.js).

Development and production are distinct DreamHost/PM2 deployments, with separate hostnames, ports, environment files, and release paths. Production deployment is a manually dispatched GitHub workflow with a protected environment, full validation, readiness check, and rollback on failed activation. The `/ready` gate currently checks generated collection-statistics and lock-video files, not classification data readiness. Server changes and frontend changes therefore have separate release timing and a cross-repository API contract to manage. [Deployment topology](../.agents/references/deployment-topology.md), [production releases](../.agents/references/production-releases.md), [runtime config](../src/config/serverRuntimeConfig.js).

## Generated data and external integrations

The active incremental exporters read `lockcollections`, `awards`, and `evidence` through their change-index collections, then write raw/state files and derived public/API JSON. `collectionStatsByIdFull.json` and `lockVideos.json` live in `COLLECTION_API_DIR`; the API reads them, and readiness requires both. Catalog utilities can read `data.json` and related catalogs from `LPU_CATALOG_DIR` snapshots or bounded HTTPS, and an optional downloader refreshes snapshots atomically. These are reusable patterns for a classification summary or for joining current site catalog data, **not an existing classification projection or guaranteed live catalog feed**. The current exporters do not index classification votes or actions. Adding classification to this pipeline would require a new source/change-index strategy, output privacy classification, refresh schedule, and ownership of stale or failed exports. [Collection pipeline](../src/projects/collections/README.md), [catalog loader](../src/util/catalogData.js), [catalog downloader](../src/projects/collections/catalogSnapshotDownload.js).

The frontend repository owns the manual lock Sheet import and static site deployment. In the current workflow, the changelog is announced from Export output, the lock catalog Sheet is updated, and its GitHub Import action runs; a successful Import triggers the site build/deploy. The target is for published changes to appear on the site within 2–3 days. Reconciliation is manual and calls for a view comparing changelog intentions with current site data for included locks; validating site display against the Sheet or tracking implementation progress is not currently required. This Node service neither runs that GitHub import nor updates the classification Sheet. Its `googleapis` use is for a separate RAFL utility and currently includes read-only Sheets scope, so a future changelog-to-Sheet write should be evaluated as new integration work. [Frontend classification overview](../../lpu-belt-explorer/internal-docs/classification-functionality-overview.md), [frontend Import workflow](../../lpu-belt-explorer/.github/workflows/import.js.yml), [Google authorization](../src/projects/raflFormUtilities/googleAuthorization.js).

## Questions this inventory leaves for the strategy decision

1. Which record is canonical for modern votes, admin actions, publication events, and the current lock belt? Choose stable IDs, round boundaries, timestamp authority, and whether immutable publication snapshots coexist with mutable actions before defining endpoints.
2. Which reads need a direct Firestore listener, a bounded server query, or a generated summary? The own-vote indicator and admin worklist have stronger freshness needs than archive/history; server HTTP alone does not supply live updates.
3. If this API owns classification writes, what transactions or conditional updates enforce one editable vote per `(entryId, userId)`, owner/admin deletion, published-action immutability, status transitions, and idempotent changelog publication? Existing services do not yet model these rules.
4. How will the server verify the profile-based `blackBelt` reader role without relying on a stale public summary or client claim, and how will denied access be tested for every vote/detail/write endpoint?
5. If a projection is used, what can safely be public, what must remain role-gated, and how is it refreshed or invalidated? Keep comments/media URLs out of public generated files.
6. For the manual reconciliation view, should the frontend compare its loaded static catalog with published changelog snapshots directly, or should this API provide a bounded comparison response using a catalog snapshot? The latter needs an explicit catalog-version/freshness contract; neither path requires Sheet-to-site validation now.

When adding a versioned endpoint, follow the existing route/service split and update OpenAPI, the readable API guide, samples, mocked service and Supertest route tests, and the consuming frontend together. Test Firebase target selection, role denial, response privacy, rate limits, cache headers, concurrency, and failure behavior with fixtures; do not run live exporters or deploy as part of routine design validation.
