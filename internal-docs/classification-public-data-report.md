### Contract decisions captured

- One vote document per `(entryId, userId)`, with a deterministic server-derived `v_` SHA-256 document ID and the original imported ID in `sourceId`. Synthetic `u_...` identities remain distinct and admin-managed.
- `classificationEntries` is a rebuildable, role-gated summary with compact vote chips and current-vote aggregates, subscribed only inside Classification. A separate minimal `classificationEntryStates` projection carries `decisionMilestoneAt`, a durable `reopened` flag, and voter IDs to match a member's own votes. Lock and scorecard routes subscribe to that state and the signed-in member's votes, without downloading other voters' chips or detail. Comments, media URLs, and admin notes stay out of both projections.
- The existing `EntryClassificationVote` guard hides other users' current and previous votes outside Classification, and its duplicate “current votes” chip summary has been removed. Row and admin-preview chips still need the Classification summary. The preview still bundles static sample votes on lock routes; the planned reader split, not the render guard, provides the intended loading and read-cost boundary. Full vote detail is requested only for an expanded lock inside Classification and released on exit.
- `reopened=true` makes all modern votes current until the next Publish or Settle, including intermediate Pending/Staged work. A new decision milestone is set only on transition to Published/Settled. A later Sheet import cannot move it. Editing an older vote moves that one canonical vote into the current set.
- Full vote detail is a bounded eligible-reader API response. Staged changelog notes are visible to eligible readers; `adminNote` is returned only through the admin action detail and is excluded from publication snapshots. Published actions and publication events are immutable.
- The versioned API uses the existing `{metadata, data}` envelope and `private, no-store` for protected responses. The recommendation now names the vote/action/publication read and command paths, their key fields, access policy, expected revisions, and idempotency behavior. The endpoint contracts still need OpenAPI, exact validation limits/cursor/error-code details, and synthetic service tests in Phase 2.
- `blackBelt` is a read-only entitlement in the release policy. Vote writes require verified `admin`, `classificationAdmin`, `lpuMod`, or `classificationTeam` claims; admin action and publication writes require `admin` or `classificationAdmin`. The current UI also derives its preview vote control from `blackBelt` through `classificationTeam`, so that control needs to match the read-only policy before writes are enabled. UI preview modes and profile timestamps grant no backend permission.

### Award trust chain decision

- The authoritative eligibility record is a document in the selected Firestore database's `awards` collection with `awardId: 'da7759a9'`. Award creation and approval are outside the Classification project. `lockcollections.blackBeltAwardedAt` may still serve existing profile features, but Classification must not use it for eligibility or authorization.
- Classification uses only the verified Firebase Auth custom claim `blackBelt: true` for Black Belt access. Auth claims are the authorization source; `user-claims-info/{uid}` must mirror **all** custom claims for internal lookup and verification and is inaccessible to the site. It cannot grant access.
- Current Black Belt claims are set manually in each environment. The owner reports that relevant development accounts already have the claim based on the award, and that production has 112 Black Belts plus three test accounts; this report did not inspect those records or run a migration.
- A future cron process will check new award documents and add `blackBelt: true` for newly eligible users. Status is normally set once per user, with little change expected outside testing. An explicit `blackBelt: false` is a manual revocation and must never be changed by automation, even when the award still exists. Every claim change must preserve unrelated custom claims and update the mirror. The initial migration tool is [migrateBlackBelts.js](../scripts/migrateBlackBelts.js); the cron and audit tools remain to be developed, with audit requirements to be defined.
- The existing migration tool selects users from `awards`, reads `lockcollections` only for display names and optional profile comparison, and skips both existing `true` and explicit `false` claims. Its current mirror write occurs only when it changes the Auth claim; Phase 6 must verify and repair mirror parity for unchanged claims as well. Because both Firestore databases share Firebase Auth, environment-specific processing must account for the user-level claim across them. Validate award-write protections before automating grants and define token refresh and acceptable revocation delay before protected reads rely on the claim.

### Phase 2 physical sizing baseline and checks

The checked-in [historical vote archive](../src/data/classification-votes-historical.json) has 2,396 records across 487 `entryId` values: 4.92 records per represented entry on average, a minimum of 1, and a maximum of 33 for `2ae1e0b8`. These historical votes stay in release-versioned JSON and do not populate the proposed modern-vote projections. The project owner confirms that [classification-samples.json](../src/data/classification-samples.json) is up to date with the current system. It has 351 modern vote records across 226 `entryId` values: 1.55 votes per represented entry on average, a minimum of 1, and a maximum of 6 for each of `9ae8b650` and `6cb514ea`. Six is the observed current maximum, not a future capacity limit.

Full-summary and minimal-state document sizes depend on the final field encoding and the number and length of modern vote chips or voter IDs. Per-route listener reads depend on the implemented queries, matching document counts, and update frequency. Batch-publish transaction size depends on the implemented write set and number of included actions. Those values cannot be calculated from either JSON file alone. During Phase 2, measure them with bounded synthetic fixtures and the confirmed Standard-edition design, including a stress case above the observed six-vote concentration and for staged actions. Instrument route tests to confirm that lock and scorecard routes read only the owner's votes and matching minimal states, with no full-summary subscription or other-vote detail request.

### Phase 2 publication validation work

No additional owner decision is needed to define the validation details. The [logical and API contract](./classification-public-data-recommendation.md#phase-1-logical-and-api-shape-decisions) already fixes the fields, roles, revision/idempotency behavior, and publication paths. Phase 2 will specify exact limits and error codes in OpenAPI, enforce them on the server, and test accepted boundaries and rejected requests.

- **Field limits:** choose bounded lengths for vote comments and media URLs, changelog notes, and admin notes without rejecting current source content. The longest checked-in modern comment is 910 characters; the admin-action JSON is test data, not a production-size sample. Validate allowed belts, action/target combinations, URLs, and all text limits server-side.
- **Pages and cursors:** choose bounded default and maximum page sizes for vote detail, staged actions, and publication history; use stable sort keys and reject malformed or mismatched cursors. Verify that pagination neither skips nor repeats records when pages are read in order.
- **Retry retention:** choose and document a finite lifetime for `Idempotency-Key` operation records and the response after expiry. Test same-key retries, changed-payload conflicts, and a lost publication response. The existing contract requires safe retries after a timeout, but sets no unusually long replay period.
- **Action transitions and errors:** encode the agreed nonpublished status changes, immutable Published actions, Staged-only batch publication, and single-action Publish Now semantics. Define stable machine-readable codes for invalid input or cursors, access denial, missing records, stale revisions, duplicate votes, invalid transitions, and idempotency conflicts; keep the agreed HTTP status classes.

These are implementation choices under the existing contract. Bring a choice back to the owner only if it would reject existing content or change the agreed workflow or retry expectation.
