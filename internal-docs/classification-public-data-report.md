### Contract decisions captured

- One vote document per `(entryId, userId)`, with a deterministic server-derived `v_` SHA-256 document ID and the original imported ID in `sourceId`. Synthetic `u_...` identities remain distinct and admin-managed.
- `classificationEntries` is a rebuildable, role-gated summary with compact vote chips and current-vote aggregates, subscribed only inside Classification. A separate minimal `classificationEntryStates` projection carries `decisionMilestoneAt`, a durable `reopened` flag, and voter IDs to match a member's own votes. Lock and scorecard routes subscribe to that state and the signed-in member's votes, without downloading other voters' chips or detail. Comments, media URLs, and admin notes stay out of both projections.
- The existing `EntryClassificationVote` guard hides other users' current and previous votes outside Classification, and its duplicate “current votes” chip summary has been removed. Row and admin-preview chips still need the Classification summary. The preview still bundles static sample votes on lock routes; the planned reader split, not the render guard, provides the intended loading and read-cost boundary. Full vote detail is requested only for an expanded lock inside Classification and released on exit.
- `reopened=true` makes all modern votes current until the next Publish or Settle, including intermediate Pending/Staged work. A new decision milestone is set only on transition to Published/Settled. A later Sheet import cannot move it. Editing an older vote moves that one canonical vote into the current set.
- Full vote detail is a bounded eligible-reader API response. Staged changelog notes are visible to eligible readers; `adminNote` is returned only through the admin action detail and is excluded from publication snapshots. Published actions and publication events are immutable.
- The versioned API uses the existing `{metadata, data}` envelope and `private, no-store` for protected responses. The sibling OpenAPI/README and local routes now document and enforce the vote/action/publication paths, bounded fields/pages/batches, expected revisions, and seven-day idempotency retention. Focused synthetic service and route tests cover the core paths; target-environment smoke tests remain before enabling readers or writes.
- `blackBelt` is a read-only entitlement in the release policy. Vote writes require verified `admin`, `classificationAdmin`, `lpuMod`, or `classificationTeam` claims; admin action and publication writes require `admin` or `classificationAdmin`. The current UI also derives its preview vote control from `blackBelt` through `classificationTeam`, so that control needs to match the read-only policy before writes are enabled. UI preview modes and profile timestamps grant no backend permission.

### Phase 2 publication validation work

No additional owner decision was needed for validation limits. The [logical and API contract](./classification-public-data-recommendation.md#phase-1-logical-and-api-shape-decisions) fixes fields, roles, revision/idempotency behavior, and publication paths. The local Node implementation uses the following limits and errors; they must be reviewed against the complete migration source and exercised in the target emulator before release.

- **Fields and batches:** 2,000 characters for vote comments, 2,048 for HTTP(S) media URLs, 4,000 for public and admin notes, 128 for IDs and display names, and at most 25 selected actions per batch. The longest checked-in modern comment is 910 characters. The belt enum and action/target combinations are checked server-side. The current export has no belt outside the enum.
- **Pages and cursors:** default 25, maximum 100 for vote detail and publication history; staged actions have a bounded 25/default, 100/maximum list. Vote detail sorts by `updatedAt` descending with Firestore's document-ID tie break and rejects stale entry revisions. Publication history sorts by `lastPublishedAt` descending with the same tie break. Malformed or missing cursor documents return `invalid_cursor`; target-emulator pagination boundary tests remain.
- **Retry retention:** command operations record request digest and response for seven days, with planned Firestore TTL on `expiresAt`; same-key/same-payload retries return the stored result and changed-payload retries return `409 idempotency_conflict`. After TTL deletion, the same key may execute again, so clients must not retry an uncertain publication indefinitely; use the publication list/detail to reconcile older timeouts.
- **Transitions and errors:** only nonpublished actions are editable; batch publication requires Staged and `omitChangelog=false`; single Publish Now applies the complete saved decision and leaves unrelated staged actions alone. The API uses `invalid_request`/`invalid_cursor` (400), `unauthorized` (401), `forbidden` (403), missing-resource codes (404), and `revision_conflict`, `duplicate_vote`, `idempotency_conflict`, or invalid-transition codes (409). Stale revision and duplicate-vote errors include the current record for recovery. Focused tests cover replay, changed-payload conflict, ownership, immutable publication, and the selected-action boundary.

These are implementation choices under the existing contract. Bring a choice back to the owner only if it would reject existing content or change the agreed workflow or retry expectation.
